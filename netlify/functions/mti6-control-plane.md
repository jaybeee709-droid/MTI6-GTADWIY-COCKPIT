This is the SPECIFICATION for the authenticated boundary. Enforcement
code lands only where it can be tested without a live identity
provider (see §5). Nothing here creates a Cloudflare account, spends
money, connects STAR, or moves Transitland.

Ruled inputs: U24(a) Workers + SQLite Durable Objects; U25(c) Google
signed JWT; U26(a) Netlify / Cloudflare coexistence. D-alpha
assumption (for Daniel to confirm or reverse): P9 builds on the
Netlify proxy first with a host-agnostic client contract, so the
Cloudflare port is a re-host, not a redesign.

## §1 Entry point shape

- The Control Plane is a Cloudflare Worker (`workers/control-plane.ts`,
  `wrangler.toml`, Free plan). It accepts `POST` only, JSON body
  `{ action, payload }`, the same envelope as the Netlify proxy:
  `{ ok, source, data | error: { code, message }, timestamp }`.
  `source` is `"control-plane"` for this Worker, never `"gateway"`.
- The Netlify proxy (`/.netlify/functions/mti6-proxy`, `/api/mti6`)
  remains the gateway until this Worker is deployed AND its JWT gate
  is enforced AND tested. U26(a) coexistence means both can serve;
  the client contract (`crypto.*` actions, envelope, error codes) is
  host-agnostic by design.
- The Worker exposes one fetch handler and one queue consumer
  (`WORKER_JOBS`). No other entry points exist in P1.

## §2 Google JWT verification design (U25(c))

- Tokens are Google-issued signed JWTs (RS256). Verification:
  1. Fetch the Google JWKS from the provisioned `GOOGLE_JWKS_URL`.
  2. Verify the RS256 signature against the matching JWKS key.
  3. Check `iss` === provisioned `GOOGLE_JWT_ISSUER`,
     `aud` === provisioned `GOOGLE_JWT_AUDIENCE`, `exp` in the
     future. Tokens are short-lived.
  4. Revocation is by token expiry plus a blocklist held in Durable
     Object state — never a shared long-lived token.
- The bearer token travels ONLY in the `Authorization: Bearer`
  header, server-side. It is never logged, never echoed, never
  stored in the PWA, the repo, or client JS.
- Until Daniel provisions Google identity (JWKS URL + issuer +
  audience in the Cloudflare dashboard), `verifyGoogleJwt()` reports
  `NOT_PROVISIONED` and the gate refuses to enforce. The Worker must
  never silently enforce a boundary no client can satisfy.

## §3 Per-action auth gate placement

- In the Netlify proxy the gate seam is `requireControlPlaneAuth()`,
  called BEFORE the `switch (action)` dispatch
  (`mti6-proxy.mjs:1315` at d24b32d). In the Worker the same seam
  runs at the top of the fetch handler, before capability routing.
- In P1 the seam is DISABLED by explicit flag
  (`CONTROL_PLANE_AUTH_ENFORCED = false` in both files, with a
  comment citing U25(c) and the missing identity provisioning). It
  returns the would-be decision for the harness to assert (valid JWT
  → allow; missing/invalid → `AUTH_REQUIRED`) and changes no
  behaviour. Enforcement flips only in a later package after Daniel
  provisions Google identity and a client is proven to pass the gate.
- `gateway.status` reports the flag honestly:
  `controlPlane: { authEnforced: false, jwtRequired: false }` until
  enforcement flips. The harness asserts `authEnforced: false` in P1.

## §4 Secret isolation

- Keys live ONLY in the server environment (Netlify encrypted fields
  today; Cloudflare secrets when the Worker is provisioned), entered
  by Daniel. They are never in the repo, the PWA, client JS, chat,
  screenshots, or messages. `KEY STORED ≠ connected` holds at every
  step: KEY STORED → BACKEND CONFIGURED → CONNECTION TESTED →
  PROVIDER AVAILABLE → STAR ROUTING AUTHORIZED.
- The proxy/Worker read env names literally (`readPipelineKeys()`,
  `readStarConfig()`, `readTransitlandKey()` in the proxy) so the
  posture generator can mechanically extract every env NAME. No key
  value is ever logged or echoed; envelopes carry provider names only.
- The posture file `src/security-posture-data.ts` is GENERATED by
  `scripts/generate-security-posture.mjs` — do not edit by hand.
  (P9 correction: the generator's hard-coded `expectedActions` list
  is stale at 7 actions while the proxy allowlist is 14; P9 updates
  the list to the full allowlist + the 5 new `crypto.*` actions and
  regenerates. The generator throws on any unreviewed allowlist
  change — that is the owner-review tripwire, and P9 updates it
  deliberately with the change recorded in the commit message.)

## §5 Spending-limit fail-safe

- Free plan only, everywhere. No auto-upgrade (hard-coded rule in
  `js/quota-config.js`, not a flag). Overuse fails safe: requests
  past the free limits are refused, never billed.
- The Netlify function has no spend cap; the quota governors are
  client-side until the Control Plane enforces them server-side in a
  later package. P3 records the ruled budgets as data
  (`js/quota-config.js` + `src/quota-config.ts`) and the router /
  React governors enforce them client-side (this-device counts only;
  provider dashboards stay authoritative).
- Cloudflare's own quotas (Workers 100,000 req/day, 10 ms CPU /
  invocation; DO 100,000 req/day, 13,000 GB-s/day, 5 GB storage) are
  recorded in `js/quota-config.js` flagged UNVERIFIED-against-docs
  until re-checked at provisioning time. GitHub compute (Actions
  minutes / AI Credits) is recorded UNKNOWN until measured. Never
  assert a number without a ruling or a dashboard reading.

## §6 Error vocabulary

| Code | Meaning | HTTP |
|---|---|---|
| `AUTH_REQUIRED` | Missing key, rejected key, or (once enforced) missing/invalid JWT | 401 |
| `QUOTA_EXHAUSTED` | Monthly/daily budget block (P1 adds the code; P3/P9 use it) | 429-class (see note) |
| `RATE_LIMITED` | Per-minute/per-second rate limit; pass through `Retry-After` if present, never assume one | 429 |
| `UPSTREAM_ERROR` | 5xx / network failure upstream; static message only, never echo upstream bodies | 502 |
| `NOT_CONFIGURED` | No key configured for a keyed action (STAR/geo pattern) | 503 |
| `INVALID_REQUEST` | Validation failure (closed params, unknown keys) — before any upstream call | 400 |
| `UNSUPPORTED_ACTION` | Action not on the allowlist | 400 |
| `NOT_FOUND` | Upstream 404 (unknown coin id, unknown resource) | 404 |

Note: `QUOTA_EXHAUSTED` is a budget block, not a rate limit. The
proxy returns it with a 429 status (same class as `RATE_LIMITED`)
but the code is distinct so clients can tell "budget gone for the
month" from "too fast right now" and serve cached/`STALE` or
`NO_DATA` with zero retries. Never a zero, never an invented value.
